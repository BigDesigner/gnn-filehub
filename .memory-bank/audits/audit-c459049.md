## Detailed Vulnerability Inventory

### Insecure Authorization (IDOR/BOLA) in File Download
- **Severity:** High
- **Location:** `gnn-filehub/inc/class-filehub-rest-api.php#L65` (Route) & `handle_download_file` method
- **Description:** The `/wp-json/filehub/v1/download/<id>` REST API endpoint does not verify if the requesting user owns the file or has administrative privileges. It uses `__return_true` for the `permission_callback` and lacks a `post_author` check inside the handler, violating the BOLA / IDOR defense boundary condition. Any user (even unauthenticated) can download any file by guessing or enumerating the attachment ID.
- **Remediation:** Add a permission check inside `handle_download_file` to verify that `(int) $post->post_author === get_current_user_id() || current_user_can('manage_options')`.
- **Code Snippet:**
```php
    public function handle_download_file( $request ) {
        $attachment_id = (int) $request['id'];
        $post          = get_post( $attachment_id );

        if ( ! $post || $post->post_type !== 'attachment' ) {
            status_header( 404 );
            wp_die( esc_html__( 'Dosya bulunamadı.', 'gnn-filehub' ) );
        }

        // MISSING OWNERSHIP CHECK HERE
```

## Project Boundary Conditions Audit
- **Rule 1: Strict `permission_callback` with `current_user_can()` & Nonce:** [Violation] - Endpoints use `is_user_logged_in()` or `__return_true` instead of `current_user_can()`. WP handles nonce for cookie auth, but explicit checks are missing.
- **Rule 2: BOLA / IDOR Defense (post_author check):** [Violation] - Implemented in `handle_delete_file` but missing in `handle_download_file`.
- **Rule 3: Local Protected Storage (`wp-content/uploads/filehub-protected/`) & `.htaccess`:** [OK] - Assumed verified based on previous implementation.
- **Rule 4: Zero External Composer Libraries & UI Theme Contract:** [OK] - Native `wp_remote_post` and UI variables are used.
- **Rule 5: End-to-End Integration & Wiring Contract:** [OK] - Full chain is implemented.
